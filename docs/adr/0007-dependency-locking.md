# ADR 0007: 本番イメージの依存だけをハッシュ付きで固定する

- ステータス: 採用
- 日付: 2026-07-31

## 背景

依存の指定が全て `>=` で、上限もロックファイルも無かった。

```
google-genai>=1.0.0
```

この状態で staging を再ビルドしたところ、`google-genai` が 2.14 から 2.16 に上がり、
Gemini の呼び出しが常に 503 になった。

```
Cannot send a request, as the client has been closed.
```

厄介だったのは**同じコードなのに prod では再現しなかった**こと。
prod のイメージは以前ビルドされたもので古い版が入っており、staging だけ新しい版が入っていた。
「環境依存の不具合」に見えてしまい、原因がライブラリのバージョン差だと分かるまで
prod と staging の両方を突き合わせる必要があった。

コード側は修正したが、同じ形の事故は他のライブラリでも起こる。

## 決定

**本番イメージに入る依存だけを、推移依存まで含めてハッシュ付きで固定する。**

| ファイル | 役割 |
|---|---|
| `app/requirements.in` | 人が編集。直接依存だけ。緩い指定でよい |
| `app/requirements.lock` | 自動生成。全推移依存をハッシュ付きで固定 |
| `requirements.txt` / `requirements-dev.txt` | ETL・開発・CI 用。**ロックしない**（上限だけ付ける。「追記」を参照） |

- Dockerfile は `pip install --require-hashes -r requirements.lock` のみ
- 再生成は `make lock`。**本番と同じ `python:3.12-slim` の中で実行する**

## 理由

### なぜ本番だけなのか

固定の価値は「本番に何が入っているかを特定できること」と
「prod と staging が同じであること」にある。開発環境や CI は多少ズレても、
壊れれば手元で気づけるし、新しい版で早めに問題を踏めるのはむしろ利点になる。

全部固定すると依存更新のたびに再生成が要り、運用の手間に対して得るものが小さい。
リリース単位で一意性が要る本番と、日々動かす開発とで扱いを変える。
これは ADR 0006 で「本番だけタグにする」と決めたのと同じ考え方。

### なぜハッシュ付きなのか

バージョン固定だけでは、同じバージョン番号で中身が差し替えられた場合を防げない。
`--require-hashes` はハッシュが一致しないものを一切インストールしないため、
ロックを更新し忘れたときもビルドが失敗して気づける。
気づかないまま別物が本番に出るよりよい。

### なぜ docker 経由で生成するのか

ロックは解決した Python バージョンに紐づく。
ローカルの venv は 3.14、本番イメージは 3.12 のため、
ローカルで生成すると本番で入らないロックができる。
`make lock` が `python:3.12-slim` を使うのはこのため。

## 帰結

- prod と staging に同じものが入ることが保証される
- 本番イメージの内容がリポジトリの1ファイルから完全に再現できる
- 依存を変えるときに `make lock` の実行が必須になる（忘れるとビルドが失敗する）
- 開発側の依存は緩いままなので、日々の更新の手間は増えない

## 追記（2026-08-06）: ETL・CI の依存は「上限だけ付けて、ロックはしない」

issue #82。上の決定では ETL・開発・CI の依存を「緩いまま」としていたが、
**上限が無いこと**が問題になったため、そこだけ見直した。

### きっかけ

ETL の品質チェック（#73）で `series.dtype == object` による文字列列の判定を書いたところ、
pandas 3 では文字列列の dtype が `object` ではなく `str` になるため常に False になり、
空文字を欠損として数え損ねていた。

このときの状況を整理すると、**上限の有無と、ロックの有無は別の問題**だと分かる。

- 壊れたこと自体は CI のテストが拾った。「新しい版を早めに踏むのは利点」という上の判断は、
  この件に関しては期待どおりに働いた
- 一方で、**上限が無いために「いつ踏むか」を選べなかった**。
  pandas 3 は誰も上げていないのに、ある日ビルドした環境にだけ入る。
  開発コンテナ（`docker/Dockerfile`）はイメージのビルド時に `requirements.txt` を入れるので、
  イメージを作った日によって手元の pandas が違う状態になっていた

### 決定

`requirements.txt` / `requirements-dev.txt` に **メジャー版の上限を付ける**。
ハッシュ付きのロックはしない。追従は Dependabot（`.github/dependabot.yml`）に任せる。

```
pandas>=2.2.0,<4     # 上限を上げるのは意図的な変更として PR で行う
```

`ruff` だけは 0.x でマイナーごとに規則が変わるため、マイナーで止めている（`<0.17`）。

### なぜロックまではしないのか

`requirements.txt` は **ETL が使うもので、ETL は本番データを書き換える**。
「本番アプリと同格に扱ってロックすべき」という理屈は成り立つ。それでもしない理由は2つ。

1. **ETL には「本番環境」が無い。** いま `make etl` を実行できるのは開発者の手元と
   開発コンテナだけで、CI やスケジューラからは動かしていない。
   ロックが守るのは「特定の環境の再現性」だが、その特定の環境がまだ存在しない
2. **CI をあえて新しい版で走らせておきたい。** `requirements-dev.txt` は
   `app/requirements.in`（本番の直接依存を緩い指定で書いたもの）を読み込んでいる。
   これは意図的で、`make lock` で版を上げるときに問題になる変更を CI が先に踏んでくれる。
   ここをロックすると、この早期警戒が無くなる

なお pip はハッシュ付きの行が1つでもあると install 全体がハッシュ検査モードに入るため、
`requirements-dev.txt` が `-r` で読む先の一部だけをロックすることもできない。

### 再検討する条件

**#32（データ更新の自動化）で ETL を CI／スケジューラから自動実行するようにしたら、
その時点で `requirements.txt` をロックする。** 上の理由1が消えるため。

## 積み残し

- `app/requirements.in` と `app/requirements.lock` のずれを検出する仕組みが無い。
  `.in` にだけ依存を足してロックを作り直し忘れても、ロック自体は自己完結しているので
  イメージのビルドは通ってしまう。CI で `pip-compile` の結果を差分比較するのが次の一手
- Dependabot は `app/requirements.lock` を扱えない（`make lock` を実行できず、
  生成には `python:3.12-slim` が要る）。`app/requirements.in` を更新する PR が来たら、
  マージ前に `make lock` を回して同じ PR にロックを含めること
