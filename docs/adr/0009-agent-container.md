# ADR 0009: Claude Code を常駐コンテナで動かし、その中では自由に操作できるようにする

- ステータス: 採用
- 日付: 2026-07-31

## 背景

Claude Code をサーバー上の tmux で常駐させ、スマホの Claude アプリから
そのセッションに指示を送って開発したい、という要求があった。
パソコンを開かずに作業を進められるためで、そのためには承認を挟まずに
（sudo も含めて）自由に操作できる環境が要る。

Claude Code（2.1.220）に OS レベルのサンドボックスは内蔵されていない。
用意されているのは権限チェックを外す仕組みだけで、位置づけはこう書かれている。

```
--dangerously-skip-permissions   Bypass all permission checks.
                                 Recommended only for sandboxes with no internet access.
```

つまり**サンドボックスは自分で用意する**という前提になっている。

最初に作った devcontainer（PR #7）は VS Code で開く前提かつ環境をそろえるのが目的で、
常駐用途に合わないうえ、隔離としても穴があった。

1. `/var/run/docker.sock` をマウントしていた。コンテナから特権コンテナを起動して
   ホストの `/` をマウントできるため、**実質ホストの root 相当**
2. `~/.config/gcloud` を丸ごとマウントしていた。dev 用の認証だけでなく
   **本人の editor 権限の認証まで見えていた**
3. 外向き通信が無制限だった

この状態で承認を全て外すのは危険だった。

## 決定

**docker compose で常駐するコンテナを隔離境界とし、その内側では自由に操作できるようにする。**

VS Code 前提の devcontainer.json は捨て、`docker/compose.yaml` に置き換えた。
tmux は**ホスト側**で回し、そこから `docker exec` でコンテナに入る。
コンテナを作り直しても tmux セッションが生き残り、イメージ更新で作業が飛ばない。

| 対処 | 内容 |
|---|---|
| docker ソケットを渡さない | マウントを削除。docker CLI も入れない |
| 認証は1ファイルだけ | `claude-dev-adc.json` を read-only で bind |
| 外向き通信を許可リスト化 | 起動時に `init-firewall.sh` で iptables + ipset |
| コンテナ内の sudo | **残す**（自由に操作するのが目的のため） |
| Claude Code 本体 | ホストの `~/.local/share/claude` を read-only でマウント |

許可する宛先は Google（`goog.json`）、GitHub（`api.github.com/meta`）、
PyPI、Anthropic API。それ以外への送信は落とす。

## 理由

### なぜ docker ソケットを外せたのか

`make lock` のために渡していた。ロックは解決した Python のバージョンに紐づき、
本番は 3.12、ホストは 3.14 だったため docker で 3.12 を用意する必要があった。

**devcontainer 自体が 3.12 なので、その中では docker が要らない。**
`make lock` を「3.12 ならそのまま、違えば docker」に変えて依存を消した。
隔離のために機能を諦めたのではなく、前提が変わって不要になった。

### なぜ Claude Code をイメージに入れないのか

インストーラを叩くとイメージのビルド時期でバージョンがホストとズレる。
ホストの `~/.local/share/claude` をそのままマウントすれば必ず一致し、
`~/.claude` を共有することでログインも引き継げる（コンテナ側で認証し直さずに済む）。
ネイティブバイナリだが Debian 上でそのまま動くことを確認した。

### なぜ通信を絞るのか

承認なしで何でも実行できる状態では、プロンプトインジェクションでデータを
外部に送られても止められない。完全遮断は GCP も GitHub も使えなくなるので採れない。
宛先を絞れば、少なくとも「知らない場所に送られる」経路は塞げる。

### なぜコンテナ内の sudo を残すのか

自由に操作できることが目的だからで、そこを削ると要求を満たさない。
コンテナは壊れても作り直せるので、内部の権限を制限する意味が薄い。

### この仕組みの限界

- コンテナ内の利用者は sudo を持つため、その気になれば `iptables -F` で firewall を消せる
- ホスト側で本人の GCP 認証を直接使えば、その権限どおりのことができる
- 許可リストは起動時に IP を解決しているので、宛先の IP が変わると繋がらなくなる

**事故と自動化の暴走を防ぐ層であって、意図的な回避を防ぐものではない。**
ADR 0008 に書いた限界と同じ性質のもの。

## 帰結

- コンテナ内では sudo を含めて自由に操作できる。壊しても作り直せば戻る
- 被害範囲がコンテナと dev 環境に閉じる。ホストと staging / prod は影響を受けない
- `make lock` が docker 非依存になり、devcontainer だけで完結するようになった
- 許可リストに無い宛先へ通信する必要が出たら `init-firewall.sh` の変更が要る
  （PR に残るので、何を許可したかが履歴として追える）
- Chromium は共有メモリを多く使うため `shm_size: 1gb` が要る。
  docker の既定 64MB では E2E が 22 件中 20 件エラーになった
