# ADR 0005: E2E はスタブと実データの2段構えにする

- ステータス: 採用
- 日付: 2026-07-25

## 背景

このアプリの不具合は**画面を操作しないと分からないもの**が多い。実際に本番へ出てしまった例:

- スマホで詳細シートの閉じるボタンが表示されない（CSS の記述順で `display:none` が後勝ち）
- スマホでグラフが画面外にはみ出す（`layoutstop` の購読先を誤り fit が走らない）
- ノードからラベルがはみ出す（cytoscape の `text-wrap` は空白でしか折り返さない）

いずれもユニットテスト・API テストをすり抜ける。ブラウザで動かさないと検出できない。

一方、E2E を実環境だけに対して回すと、GCP 認証が必要になり PR ごとの高速な検証ができない。
スタブだけに対して回すと、BigQuery のスキーマ変更やデータ欠損を検出できない。

## 決定

**同じ E2E テストを、2つの対象に対して実行する。**

| タイミング | 対象 | 目的 |
|---|---|---|
| PR | スタブ版アプリ（ローカル起動） | 高速フィードバック。GCP 認証不要で全員が回せる |
| main マージ後 | **staging（実データ）** | 実 BigQuery・実データでの本番前ゲート |
| 本番デプロイ後 | prod | `smoke` マーカーの最小確認のみ |

テストコードは共通で、`E2E_BASE_URL` の有無で対象が切り替わる。

```bash
make e2e                      # スタブ版を自動起動して実行
make e2e-smoke ENV=staging    # デプロイ済み staging に対して実行
E2E_BASE_URL=https://... pytest e2e   # 任意の環境に対して全件実行
```

## 実装

- `e2e/server.py` — BigQuery と Gemini をスタブに差し替えて FastAPI を起動する
- `e2e/fake_data.py` — 実データに似せたスタブ応答（クエリ内容で返す行を出し分ける）
- `e2e/conftest.py` — `E2E_BASE_URL` が無ければスタブ版を起動、あればその URL を使う

## 理由

- **スタブ版は決定的**。データの中身に依存しないので、CI がデータ更新で不安定にならない
- **staging 実行は本物**。スタブでは絶対に見つからない「BigQuery の列を消した」
  「ETL がデータを入れ損ねた」といった問題を、本番の手前で止められる
- テストコードを共通にすることで、二重メンテを避ける

## テストを書くときの注意

staging の実データに対しても通る書き方にする。

- ❌ 「制度が3件表示される」のような件数への依存
- ⭕ 「1件以上表示される」「制度ノードは1つだけになる」のような構造への依存
- 特定の制度名に依存しない（自治体によってデータが変わるため）

スタブ固有のデータに依存するテストを書きたい場合は、実データでも成立する条件に言い換えるか、
どうしても必要ならマーカーで分離する。

## 帰結

導入時点で、上記の実バグ2件（閉じるボタン・グラフはみ出し）を E2E が検出した。
どちらも既存の 122 件のユニット/API テストはすべて通っていた状態で見つかっている。
