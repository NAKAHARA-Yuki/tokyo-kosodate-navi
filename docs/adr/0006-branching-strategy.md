# ADR 0006: GitHub Flow + タグでの本番リリース

- ステータス: 採用
- 日付: 2026-07-25

## 背景

チーム開発に移行するにあたりブランチ戦略を決める必要があった。
また、当初の CD は「本番デプロイ = main HEAD を手動実行」としていたが、これには穴があった。

- 「今の本番はどのコミットか」に即答できない
- 切り戻したいとき、戻す先が特定できない
- `main` に未リリースの変更が溜まっている状態で、本番だけの緊急修正を出せない

## 決定

**GitHub Flow（`main` + 短命なトピックブランチ）を採用し、本番リリースは `v*.*.*` タグで行う。**

```
main ← 常にデプロイ可能
 ├─ feat/... fix/... docs/... refactor/... chore/...
 └─ hotfix/...   （タグから切る）
```

| 操作 | 反映先 |
|---|---|
| PR | CI のみ（lint / test / E2E スタブ / Docker build） |
| `main` へ Squash merge | staging へ自動デプロイ → staging 実データで E2E |
| `v*.*.*` タグを push | 承認後に本番へデプロイ → スモーク |

- `main` へのマージは **Squash merge のみ**
- バージョンはセマンティックバージョニング
- hotfix は **タグから枝を切る**（main から切ると未リリース分を巻き込むため）

## 理由

### なぜ Git Flow ではないのか

`develop` / `release` ブランチを置く構成は、複数バージョンを並行保守する場合に効く。
本プロダクトはリリース列が1本で、`main` マージが即 staging に反映される運用のため、
`develop` は `main` の写しにしかならず二重管理になる。

### なぜ本番だけタグなのか

staging は「main の最新が動いていればよい」ので自動で十分。
一方、本番は**何が入っているかを一意に言えること**が運用上いちばん重要になる。
タグにすれば

- `v1.2.0` が本番、と一言で言える
- 切り戻しは前のタグを再デプロイするだけ
- 「staging では直っていたのに本番に出ていない」といった取り違えが起きにくい

Cloud Run のラベルに `release` と `commit` を入れ、GCP 側からも追跡できるようにしている。

### なぜ Squash merge なのか

- `main` の履歴が「1行1変更」で読める
- 切り戻しが `git revert <commit>` 1発で済む
- PR 内の試行錯誤のコミット（"fix typo" 等）が `main` に残らない

引き換えに PR 内の詳細な経緯は失われるが、それは PR のページに残るので実害は小さい。

## 帰結

- 本番の内容と切り戻し先が常に特定できる
- リリースの単位が明示的になり、変更履歴（タグ）がそのままリリースノートの土台になる
- タグを打つという明示的な操作が挟まるため、誤って本番へ出る事故が起きにくい

### 必要な GitHub 側の設定

- リポジトリ設定で **Squash merge のみ有効**にする
- `main` にブランチ保護（直 push 禁止 / CI 必須 / approve 1名以上）
- Environments に `staging` と `production` を作り、`production` に承認者を設定
