# ADR 0006: GitHub Flow + タグでの本番リリース

- ステータス: 採用
- 日付: 2026-07-25

## 背景

チーム開発に移行するにあたりブランチ戦略を決める必要があった。
また、当初の CD は「本番デプロイ = main HEAD を手動実行」としていたが、これには穴があった。

- 「今の本番はどのコミットか」に即答できない
- 切り戻したいとき、戻す先が特定できない
- `main` に未リリースの変更が溜まっている状態で、本番だけの緊急修正を出せない

## 決定

**GitHub Flow（`main` + 短命なトピックブランチ）を採用し、本番リリースは `v*.*.*` タグで行う。**

```
main ← 常にデプロイ可能
 ├─ feat/... fix/... docs/... refactor/... chore/...
 └─ hotfix/...   （タグから切る）
```

| 操作 | 反映先 |
|---|---|
| PR | CI のみ（lint / test / E2E スタブ / Docker build） |
| `main` へ Squash merge | staging へ自動デプロイ → staging 実データで E2E |
| `v*.*.*` タグを push | 承認後に本番へデプロイ → スモーク |

- `main` へのマージは **Squash merge のみ**
- バージョンはセマンティックバージョニング
- hotfix は **タグから枝を切る**（main から切ると未リリース分を巻き込むため）

## 理由

### なぜ Git Flow ではないのか

`develop` / `release` ブランチを置く構成は、複数バージョンを並行保守する場合に効く。
本プロダクトはリリース列が1本で、`main` マージが即 staging に反映される運用のため、
`develop` は `main` の写しにしかならず二重管理になる。

### なぜ本番だけタグなのか

staging は「main の最新が動いていればよい」ので自動で十分。
一方、本番は**何が入っているかを一意に言えること**が運用上いちばん重要になる。
タグにすれば

- `v1.2.0` が本番、と一言で言える
- 切り戻しは前のタグを再デプロイするだけ
- 「staging では直っていたのに本番に出ていない」といった取り違えが起きにくい

Cloud Run のラベルに `release` と `commit` を入れ、GCP 側からも追跡できるようにしている。

### なぜ Squash merge なのか

- `main` の履歴が「1行1変更」で読める
- 切り戻しが `git revert <commit>` 1発で済む
- PR 内の試行錯誤のコミット（"fix typo" 等）が `main` に残らない

引き換えに PR 内の詳細な経緯は失われるが、それは PR のページに残るので実害は小さい。

## 帰結

- 本番の内容と切り戻し先が常に特定できる
- リリースの単位が明示的になり、変更履歴（タグ）がそのままリリースノートの土台になる
- タグを打つという明示的な操作が挟まるため、誤って本番へ出る事故が起きにくい

### 必要な GitHub 側の設定（設定済み）

- リポジトリ設定で **Squash merge のみ有効**
- `main` の ruleset で 直 push 禁止 / squash のみ / CI 必須 / force push・削除の禁止
  - approve の必須数は **1**（2026-08-04 に 0 から変更）。
    ひとり体制の間は 0 にしていた。GitHub は自己承認を許可しないため、
    1 以上にすると自分の PR をマージできなくなるからである。
    メンバーが増えたので、当初から予定していた本来の運用に戻した。
    あわせて push で既存の approve を無効化する設定（`dismiss_stale_reviews_on_push`）と、
    レビューコメントの解決を必須にする設定（`required_review_thread_resolution`）を入れている
  - 必須の CI チェックは4つ。`Lint & Unit/Integration Test` / `E2E (stub)` /
    `Docker build` / `Frontend Lint & Build`

> ruleset を API から更新するときは **`PUT /repos/{owner}/{repo}/rulesets/{id}`** を使う。
> `PATCH` は 404 を返す（他の多くの GitHub API と違う点で、実際にここで詰まった）。
> `rules` は差分ではなく**全体を送る**ので、`GET` した内容を書き換えて投げ直すこと。
- Environments
  - `staging`: `main` ブランチからのみデプロイ可。承認なし
  - `production`: **`v*.*.*` タグからのみ**デプロイ可 + 承認者必須

`production` を「タグからのみ」に制限したことで、本番リリースがタグ経由であることが
ワークフローの `if` 条件だけでなく GitHub 側でも担保される。

なお ruleset は Free プランの private リポジトリでは強制されないため、
このリポジトリは public にしている（元データが東京都のオープンデータであり、
コードにも認証情報を含まないため公開して支障がない）。
