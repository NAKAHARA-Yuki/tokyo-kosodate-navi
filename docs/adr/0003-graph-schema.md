# ADR 0003: グラフスキーマとスキルツリーの生成方針

- ステータス: 採用
- 日付: 2026-07-25

## 背景

初期のグラフは `Benefit`・`Status`・`Document` の3ノードだけで、
**制度から制度へのエッジが1本も無かった**。

プロダクト構想の中核は「制度同士のシナジーや連鎖（スキルツリー）」を見せて
"貰いそびれ" を防ぐことだったが、それを表現する構造が存在していなかった。

また、同一制度が自治体ごとに別レコードとして存在するため
（「定期予防接種」が62自治体685件、「児童手当」が61自治体120件）、
全体像を俯瞰できずグラフもノイズだらけだった。

## 決定

### ノード・エッジ

| ラベル | 内容 |
|---|---|
| `Benefit` | 制度（自治体ごとの1レコード、7,812） |
| `Scheme` | 制度マスタ（自治体をまたいで束ねたもの、300） |
| `Status` | 適用条件（年齢・地域・分類、453） |
| `Document` | 必要書類（9,373） |

| エッジ | 内容 |
|---|---|
| `REQUIRES` | 制度 → 条件 |
| `REQUIRES_DOC` | 制度 → 書類 |
| `IN_SCHEME` | 制度 → 制度マスタ |
| `LEADS_TO` | **制度 → 制度（スキルツリー）** |

### スキルツリーは確定ルールで生成する

`LEADS_TO` は同一自治体内で以下の2種類だけを張る（`build_benefit_edges()`）。

| relation | 条件 | 意味 |
|---|---|---|
| `NEXT_STEP` | 年齢帯が地続き（間隔1年以内、重複なし） | 「次に来る制度」 |
| `SHARED_DOC` | 特徴的な書類を共有 | 「ついでに申請できる制度」 |

各エッジには `reason` に根拠文を持たせる（例: `対象年齢が23ヶ月→24ヶ月で連続`）。

## 理由

- **機械的に検証できる根拠だけを使う。** 年齢の連続と書類の一致はデータから確認でき、
  LLM で「関連しそう」と判定させる方式と違って再現性がある（[ADR 0001](0001-judgment-vs-llm-separation.md)）
- **同一自治体内に限定。** 他区の制度に繋がっても申請できないため
- **汎用書類は除外する。** 全体の5%超に登場する書類（保険証・マイナンバーカードなど）で
  繋ぐとエッジが爆発し、意味を持たなくなる

## 帰結

- `LEADS_TO` が 6,192本 生成され、
  「1歳6か月児健診 → 2歳児歯科健診 → 3歳児健診」のような自然な流れが辿れるようになった
- `Scheme` により 7,812件を 300の制度として俯瞰できるようになった
- `GET /api/benefits/match` が `next_steps` として「次に繋がる制度」を返せるようになった

### 実装上の注意

- **PROPERTY GRAPH には PRIMARY KEY が必須。** 各テーブルに
  `ALTER TABLE ... ADD PRIMARY KEY (...) NOT ENFORCED` を事前に実行する。
  再実行時は `DROP PRIMARY KEY IF EXISTS` を先に挟まないと "Already Exists" で落ちる
- **スキーマを変えたら `make graph` を必ず再実行する。**
  PROPERTY GRAPH は列を参照しているため、列追加だけでも定義し直しが要る

## 今後の検討

- `NEXT_STEP` は年齢の連続のみで判定しており、意味的な前後関係（例:「認定を受けてから申請」）は
  拾えていない。`conditions_text` のパターンマッチで前提関係を足す余地がある
- `Scheme` を主役にした「制度マスタ中心のビュー」は未実装
