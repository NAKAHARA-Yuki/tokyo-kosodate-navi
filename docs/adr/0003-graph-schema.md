# ADR 0003: グラフスキーマとスキルツリーの生成方針

- ステータス: 採用
- 日付: 2026-07-25

## 背景

初期のグラフは `Benefit`・`Status`・`Document` の3ノードだけで、
**制度から制度へのエッジが1本も無かった**。

プロダクト構想の中核は「制度同士のシナジーや連鎖（スキルツリー）」を見せて
"貰いそびれ" を防ぐことだったが、それを表現する構造が存在していなかった。

また、同一制度が自治体ごとに別レコードとして存在するため
（「定期予防接種」が62自治体685件、「児童手当」が61自治体120件）、
全体像を俯瞰できずグラフもノイズだらけだった。

## 決定

### ノード・エッジ

| ラベル | 内容 |
|---|---|
| `Benefit` | 制度（自治体ごとの1レコード、7,812） |
| `Scheme` | 制度マスタ（自治体をまたいで束ねたもの、300） |
| `Status` | 適用条件（年齢・地域・分類、453） |
| `Document` | 必要書類（9,373） |

| エッジ | 内容 |
|---|---|
| `REQUIRES` | 制度 → 条件 |
| `REQUIRES_DOC` | 制度 → 書類 |
| `IN_SCHEME` | 制度 → 制度マスタ |
| `LEADS_TO` | **制度 → 制度（スキルツリー）** |

### スキルツリーは確定ルールで生成する

`LEADS_TO` は同一自治体内で以下の2種類だけを張る（`build_benefit_edges()`）。

| relation | 条件 | 意味 |
|---|---|---|
| `NEXT_STEP` | 年齢帯が地続き（間隔1年以内、重複なし） | 「次に来る制度」 |
| `SHARED_DOC` | 特徴的な書類を共有 | 「ついでに申請できる制度」 |

各エッジには `reason` に根拠文を持たせる（例: `対象年齢が23ヶ月→24ヶ月で連続`）。

## 理由

- **機械的に検証できる根拠だけを使う。** 年齢の連続と書類の一致はデータから確認でき、
  LLM で「関連しそう」と判定させる方式と違って再現性がある（[ADR 0001](0001-judgment-vs-llm-separation.md)）
- **同一自治体内に限定。** 他区の制度に繋がっても申請できないため
- **汎用書類は除外する。** 全体の5%超に登場する書類（保険証・マイナンバーカードなど）で
  繋ぐとエッジが爆発し、意味を持たなくなる

## 帰結

- `LEADS_TO` が 6,192本 生成され、
  「1歳6か月児健診 → 2歳児歯科健診 → 3歳児健診」のような自然な流れが辿れるようになった
- `Scheme` により 7,812件を 300の制度として俯瞰できるようになった
- `GET /api/benefits/match` が `next_steps` として「次に繋がる制度」を返せるようになった

### 実装上の注意

- **PROPERTY GRAPH には PRIMARY KEY が必須。** 各テーブルに
  `ALTER TABLE ... ADD PRIMARY KEY (...) NOT ENFORCED` を事前に実行する。
  再実行時は `DROP PRIMARY KEY IF EXISTS` を先に挟まないと "Already Exists" で落ちる
- **スキーマを変えたら `make graph` を必ず再実行する。**
  PROPERTY GRAPH は列を参照しているため、列追加だけでも定義し直しが要る

## 今後の検討

- `NEXT_STEP` は年齢の連続のみで判定しており、意味的な前後関係（例:「認定を受けてから申請」）は
  拾えていない。`conditions_text` のパターンマッチで前提関係を足す余地がある
- `Scheme` を主役にした「制度マスタ中心のビュー」は未実装

## 追記（2026-08-01）: GQLからSQLへの切り替え

BigQuery の GQL（`GRAPH ... MATCH`）が Enterprise エディションの予約必須になり、
`/api/subgraph` と `/api/benefits/match` の `next_steps`（`_fetch_next_steps`）、
`src/verify_graph.py` の検証クエリが全環境で失敗するようになった（issue #16）。

REQUIRES / REQUIRES_DOC / LEADS_TO を辿るこれらのクエリを、通常SQLの `JOIN` に
書き換えて対応した。判断のポイント:

- **グラフとしてのデータモデル（このADRの本体）は変わっていない。** 変わったのは
  「ノード/エッジのテーブルをどのクエリ言語で読むか」だけ。`CREATE OR REPLACE PROPERTY GRAPH`
  の定義（`create_graph.sql`）はそのまま残しており、Enterprise予約なしでGQLが
  使えるようになれば戻せる。
- **判定層（`/api/benefits`, `/api/benefits/match` の絞り込み本体, `/api/timeline`）は
  そもそも通常SQLで、今回の障害の影響を受けていない。** GQLを使っていたのは
  可視化用の1ホップ探索（`/api/subgraph`）とスキルツリー探索（`next_steps`）のみ。
- **今後グラフを拡張する手順（ノード/エッジテーブルの追加、`create_graph.sql` への追記）にも
  影響しない。** 1〜2ホップ程度の探索は `JOIN` で書けるため、当面はSQLで十分。
  可変長パス探索が必要になった場合は、BigQueryの再帰CTE（`WITH RECURSIVE`）か
  Enterprise予約の購入（対応案B）を再検討する。

## 追記（2026-08-13）: GQL はいま通る

**上の「Enterprise 予約必須で失敗する」という状態は解消しています。** 実際に投げて確認しました。

| 環境 | 結果 |
|---|---|
| dev（`gov_knowledge_db_dev`） | 通る |
| staging | 通る |
| prod | 通る |

```
1ホップ  制度 → 条件                                   通る
2ホップ  制度 → 書類 → 別の制度                          通る
3ホップ  制度 → scheme → 他自治体の同一制度 → その必要書類    5件 / 1.8秒
```

**なぜ通るようになったかは未確認です。**

- Enterprise 予約が付いた（＝課金が発生している）
- BigQuery 側が制限を外した（＝オンデマンドで使える）

`claude-dev` には `bigquery.reservations.list` が無く、403 で確認できませんでした。
**owner の確認が要ります。** 前者なら「GQL に依存する設計にするか」はコストの判断になります。

### それでも JOIN のままにしている

上の追記で JOIN に書き換えた `/api/subgraph` と `_fetch_next_steps` は**戻していません。**

- **動いているものを、理由の分からない環境変化に合わせて戻すのは危険。**
  予約が誰かの操作で付いているなら、外れたときに再び全滅する
- いまアプリが投げている問いは**すべて1ホップ**で、JOIN で足りている
- 多ホップが必要になるかは #112 で「アプリが聞きたい問い」を決めてから判断する

**この ADR は「グラフのデータモデル」を定めたものであり、クエリ言語の選択とは独立している。**
GQL が使えるようになったこと自体は、モデルを変える理由にはならない。

## 追記（2026-08-20）: `REQUIRES_BENEFIT` を足した（issue #121）

「今後の検討」に挙げていた **`conditions_text` のパターンマッチで前提関係を足す**を実装した。

```
[ひとり親家庭高等職業訓練促進給付金]
  児童扶養手当の支給を受けているか、または同等の所得水準にある方
```

dev で **155本**。うち **129本が児童扶養手当を前提**にしており、
**ひとり親の方が認定されると自治体あたり平均3.5件が芋づる式に申請できる**（44自治体）。実測は `scripts/survey_requires_benefit.py`。

### なぜ NEXT_STEP より良いのか

`NEXT_STEP` の根拠は年齢が地続きなことだけで、**利用者にとって意味のある根拠ではなかった**
（この ADR 自身が認めていた）。`REQUIRES_BENEFIT` は**条件文にそう書いてある**ので、
`reason` がそのまま利用者に見せられる文になる。

```
NEXT_STEP          対象年齢が35ヶ月→36ヶ月で連続          ← 見せられない
REQUIRES_BENEFIT   条件に「児童扶養手当を受けている」とある   ← 見せられる
```

### 踏んだ罠を2つ残す

**1. 制度名の部分一致でエッジを引いてはいけない。**
「児童扶養手当」は「**特別**児童扶養手当」に部分一致するが、前者はひとり親、
後者は障害のある児童が対象で別の制度。区別せずに引くと誤ったエッジが 126本できた。
名前の直前が制度名を構成しうる文字なら別の制度とみなす（`title_refers_to()`）。

**2. 「受けていないことが条件」が同数ある。**
肯定 162件に対し否定 151件で、文の形がほとんど同じ。逆に取ると
「受けた人にだけ出す」ものが「受けた人には出さない」制度に化ける。
**同じ制度文に両方書かれている**ものがあるため、制度単位ではなく文単位で判定する。

否定側をエッジとして持つかは #29（併給関係。EXCLUDES / COMBINABLE_WITH）の範囲とした。

**3. 制度名の左端を固定する。**
末尾（`手当` `給付金`）だけを決めて最左一致に任せると、前置きごと名前として取る。

```
ひとり親家庭の父または母が児童扶養手当の支給を受けているか
  → 「ひとり親家庭の父または母が児童扶養手当」を名前として扱っていた
```

名前は**漢字かカタカナだけ**で構成し、**直前が漢字・カタカナでない**ものに限る。
直前がひらがな（助詞）や記号なら境界、漢字なら**より長い別の名前の一部**という判定。
これで `により特別児童扶養手当` から `特別児童扶養手当` を取りつつ、
`児童扶養手当`（直前が「別」）は取らない。

**頭から短くしていって一致を探してはいけない。** それをやると上の混同が復活する。

「AおよびB」は動詞が最後にしか付かないため、**並んだ名前を全部取る**必要がある。

### 引けなかったもの

参照のうち 16本は、同じ自治体に同名の制度が無くて引けていない
（`医療費助成` のように名前が一般的すぎるもの、制度名ではない文の断片、など）。
**引けない分は誤ったエッジを作らず、条件原文の提示に倒す**（#63）。
