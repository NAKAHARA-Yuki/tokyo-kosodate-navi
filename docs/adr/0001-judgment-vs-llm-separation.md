# ADR 0001: 制度の適用判定に LLM を使わない

- ステータス: 採用
- 日付: 2026-07-25

## 背景

行政制度のマッチングサービスを作るにあたり、「ユーザーの状況を LLM に渡して
対象制度を判断させる」構成は実装が容易で、自然文入力にも対応できる。

一方で本プロダクトが扱うのは、**間違えるとユーザーが不利益を被る**情報である。

- 対象なのに出ない → 受け取れたはずの給付を逃す（＝解決したい「貰いそびれ」そのもの）
- 対象外なのに出る → 窓口で断られ、無駄足と不信を生む

## 決定

**判定層と伴走層を分離する。**

| 層 | 実装 | 責務 |
|---|---|---|
| 判定 | BigQuery Graph への定型クエリ | 対象制度の確定。LLM を一切通さない |
| 伴走 | Gemini | 表現の言い換え、書類添削。判定結果は変えない |

具体的な制約:

1. `/api/benefits`、`/api/benefits/match`、`/api/timeline`、`/api/subgraph` に LLM を挟まない
2. Gemini を呼ぶのは `/api/support/draft-review` のみ
3. Gemini のプロンプトに「制度情報に書かれていないことは絶対に補わない／
   曖昧なら窓口に確認と明記する」を必ず含める
4. AI 生成物には disclaimer を添えて返す
5. プロフィール入力はチャットではなく**選択式フォーム**にする

## 理由

- **正確性**: WHERE 句の比較結果は再現可能で検証できる。LLM の判断は再現性がなく監査もできない
- **速度**: 属性マッチは数百ミリ秒で返る。メイン画面を開くたびに LLM を待たせない
- **説明責任**: 「なぜこの制度が出たか」を `match_reasons` として構造的に返せる
- **コスト**: 一覧表示のたびに LLM を呼ぶ設計はスケールしない

## 帰結

### 良い点

- マッチング結果がテスト可能になった
- 判定の根拠をユーザーに提示できる（「お子さんの月齢18が対象範囲0〜36ヶ月に該当」）
- LLM の障害・レート制限がコア機能を止めない

### 引き受けるコスト

- 自然文の条件（`has_free_text_conditions`、3,808件）は機械判定しきれない。
  → マッチはさせた上で条件文言を提示し、Gemini に補足させる方針で運用する
- 元データに構造化された年齢が無い制度が多い問題は、
  LLM ではなく**正規表現ルール**で解いた（→ [ADR 0002](0002-age-inference.md)）
- 自然文入力での検索体験は提供できない

## 代替案とその評価

- **LLM に全部判定させる**: 実装は最速だが、誤判定の説明も検証もできず却下
- **LLM で判定してルールで検証する二段構え**: 検証ルールを書くなら最初からルールで判定すればよい
- **LLM を再ランキングにだけ使う**: 将来検討の余地あり。ただし表示順が変わるだけでも
  「上位に出ない＝知りそびれ」を生むため、導入するなら根拠の提示とセットにする

## 追記（2026-08-13）: 抽出・正規化には LLM を使ってよい

このADRの「LLM を使わない」が、**ETL 時のデータ抽出・正規化まで禁じている**と読まれていた。
実際 [#76](https://github.com/NAKAHARA-Yuki/tokyo-kosodate-navi/issues/76)（所得条件の機械判定）は
「抽出は正規表現で行う（ADR 0001 により LLM は使わない）」と書かれている。

**このADRが避けたかったのは、チャットベースの LLM に適用判定をさせることであって、
ETL 時の抽出・正規化ではない。** 以後は次のように区別する。

| | 判定（リクエスト時） | 抽出・正規化（ETL時） |
|---|---|---|
| LLM | **使わない** | **使ってよい** |
| なぜ | 再現性・監査可能性・速度が要る | 結果はテーブルに落ち、人が検証できる。リクエスト経路に乗らない |

### 使うときの制約

**むやみに叩かない。必要なときに、必要な分だけ、必要なモデルを使う。**

1. **対象を絞る。** 規則で拾えたものには当てない。規則で拾えなかった残りだけに使う
2. **同じ入力で二度叩かない。** 結果はテーブルに保存して使い回す
   （[ADR 0015](0015-cache-ai-explanations.md) と同じ考え方）
3. **モデルは用途に見合うものを選ぶ。** 既定は軽いモデル。重いモデルを使うなら、
   軽いモデルで足りないことを実測してから決める
4. **バッチで回す。** リクエスト経路からは呼ばない
5. **検証可能にする。** 抽出元のテキストと確度を残し、`age_source` と同じ
   `explicit` / `inferred` / `unknown` の区別を付ける。推定を断定として見せない
   （[ADR 0002](0002-age-inference.md)）
6. **自信が無いものは判定に使わない。** 条件原文の提示に倒す（#63）

### 変わらないこと

「決定」の制約1〜5はそのまま有効。判定経路（`/api/benefits`、`/api/benefits/match`、
`/api/timeline`、`/api/subgraph`）に LLM を挟まない。**リクエスト時**に Gemini を呼ぶのは
`/api/support/draft-review` だけ。プロフィール入力は選択式フォームのまま。
