# ADR 0015: やさしい解説の生成結果を BigQuery にキャッシュする

- ステータス: 採用
- 日付: 2026-08-06
- 関連: issue #68

## 背景

`/api/support/draft-review` の「やさしい解説」は毎回 Gemini を呼んでいた。
**同じ制度に対して、何度呼んでも同じものを作り直していた。**

- 実測で **9〜13秒**かかる（`thinking_level=HIGH` を使っているので短縮の余地も小さい）
- 制度は 7,812 件あり、内容はそう頻繁に変わらない
- Cloud Run は `min-instances 0` でインスタンスが使い捨てなので、
  **プロセス内のメモリに持っても意味がない**（次のリクエストは別インスタンス）

## 決定

生成結果を BigQuery のテーブル `benefit_explanations` に保存し、2回目以降はそれを返す。

キャッシュキーは **出力を決める要素すべての sha256**。

```
sha256(benefit_id + sha256(facts) + model + prompt_version)
```

- `facts` = Gemini に渡した事実文字列そのもの
- `model` = `GEMINI_MODEL`
- `prompt_version` = 手で上げる整数（`app/explanation_cache.py`）

**`mode=review`（申請書の下書き添削）はキャッシュしない。**

## 理由

### なぜ BigQuery か

| 候補 | 判断 |
|---|---|
| **BigQuery** | 採用。既に使っているので GCP サービスも IAM もローカル開発手順も増えない |
| Firestore | 点参照は速いが、新しいサービスの追加が要る。ADR 0013 のように IAM を1つ増やすと owner の作業を挟む |
| Cloud Storage | 素朴で安いが、これも新しい権限が要る |

キャッシュとしての BigQuery は速くはない。**実測で点参照の中央値 0.86 秒**。
それでも Gemini の 9〜13 秒に対しては十分で、この差のために新しいサービスを増やす価値は無い。

点参照しかしないので `cache_key` でクラスタリングしている。

### なぜ `benefits.update_date` で無効化しないのか

`update_date` は**自治体側の更新日**であって、こちらが Gemini に渡した内容が
変わったかどうかとは一致しない。更新日が動いても渡す内容は同じことがあるし、
逆に更新日が動かなくても列の中身が変わることがある。

**渡した事実文字列そのもののハッシュ**をキーに入れれば、1文字でも変われば別キーになる。
取りこぼしも、無駄な作り直しも起きない。

### なぜ有効期限を設けないのか

出力を決める要素（制度情報・モデル・プロンプト）はすべてキーに入っている。
期限を切っても、**同じ入力から同じものをもう一度作るだけ**で、費用と待ち時間だけがかかる。

「内容は同じだが作り直したい」場合のレバーは `PROMPT_VERSION` を上げること。
これは意図的な操作として PR に残る。

### なぜ review をキャッシュしないのか

`mode=review` の入力は**利用者が書いた文章**で、氏名・世帯の事情といった個人情報が入りうる。
保存しない。参照もしない（同じ制度でも下書きが違えば別の結果になるべきで、
キャッシュを引くこと自体が誤り）。

### なぜ失敗しても例外を投げないのか

キャッシュは高速化の仕組みであって、**ここが落ちたせいで解説そのものが出せなくなるのは
本末転倒**。参照に失敗したら「無かった」として生成に進み、保存に失敗したら次回また作る。
利用者に見せる内容は変わらない。

副産物として、バックエンドの実行 SA から BigQuery に書けない構成になっても機能は動き続ける
（現在のバックエンドは `--service-account` を明示しておらず既定の compute SA で動いている。
将来ここを絞ったときに壊れない）。

## 帰結

- **2回目以降が 12.27 秒 → 1.46 秒**（dev の実データ・実 Gemini で計測）
- Gemini が落ちていても、キャッシュがあれば解説を返せる（可用性が上がる）
- 「いま作った文章」とは限らなくなるので、`generated_at` をレスポンスに含めて画面に出す
- テーブルは**初回の書き込み時に自動で作られる**（`create_table(exists_ok=True)`）。
  環境ごとの手作業を増やさないため
- ETL はテーブル単位の `WRITE_TRUNCATE` を自分の5テーブルにしか行わないので、
  **ETL を回してもキャッシュは消えない**

### 気をつけること

書き込みにストリーミング挿入（`insert_rows_json`）を使っているため、
**挿入直後の行は UPDATE / DELETE できない**（実測で 400 が返る）。

```
UPDATE or DELETE statement over table ... would affect rows in the
streaming buffer, which is not supported
```

通常の作り直しはキーが変わることで行うので運用上は困らない。
全部消したいときは `DROP TABLE` する（次のリクエストで作り直される）。

## 積み残し

- ヒット率が見えない。どこかで数えられるようにするか要検討（issue #68 の「検討の余地があること」）
- 生成日時の表示は現時点で `/debug` にしか無い。Next.js の詳細ページは #54 で対応する
- **事前生成（バッチでの先回り生成）はやらない。** 初回だけ 9〜13 秒かかることは受け入れる。
  7,812 件すべてを先に作ると、ほとんど誰も見ない制度の分まで費用がかかる（#68 でスコープ外と決めた）
