# エージェント運用ルール

Claude Code を自律的に動かすときの行動規範。**このファイルが唯一の正**とする。

有効化は、各自のセッションに次の1行を貼るだけ。

```
docs/agent-operating-rules.md を読んで、その通りに常時動いてください。
```

内容を変えたいときは、貼り直すのではなく**このファイルを PR で直す**。全員に伝播する。

`CLAUDE.md` と `CONTRIBUTING.md` の規約が最優先。本ファイルと矛盾したらそちらに従う。

## 基本ループ

15分ごとに次を繰り返す。何も無ければ何もせず次の周回へ。

**優先順位はこの順。上が終わるまで下に行かない。**
レビューと指摘対応は、新しい着手より必ず優先する。
全員が新規着手ばかりすると PR が滞留して全体が止まるため。

### 1. 受信箱を見る

```bash
gh api /notifications --jq '.[] | select(.repository.name=="tokyo-kosodate-navi") |
  {id:.id, reason:.reason, title:.subject.title, url:.subject.url}'
```

メンション・レビュー依頼・コメント・CI 失敗がここに集まる。
処理し終えたら `gh api -X PATCH /notifications/threads/<id>` で既読にする。

### 2. レビュー依頼に応える

```bash
# 自分に依頼が飛んでいる PR を探す
for n in $(gh pr list --state open --json number -q '.[].number'); do
  echo "#$n → $(gh api repos/:owner/:repo/pulls/$n -q '[.requested_reviewers[].login]|join(",")')"
done
```

**`gh pr list --search "review-requested:@me"` は使わない。** このリポジトリの `gh`
トークンは `repo` と `workflow` しか持っておらず、検索を裏で支える GraphQL が通らない。
エラーにならず **0件を返す**ので、依頼が無いと誤読する。

必ず PR 上に結果を残す。Approve するか、指摘をコメントに書く。黙って放置しない。
**approve の操作自体がブロックされている環境がある**（実際にそういうセッションがある）。
そのときは内容の確認結果をコメントに書き、approve を他の人に頼むこと。
これは「放置」ではないので、ルール違反にはあたらない。
観点は CONTRIBUTING.md の「レビューで必ず見る点」。特に次は毎回確認する。

- 判定ロジックに LLM が混入していないか
- 年齢・地域の絞り込みが `effective_*` カラムを使っているか
- 本番 BigQuery を壊す操作が意図せず入っていないか

**判断がつかないときは approve しない。** その旨をコメントに書いてリードに振る。
自分の理解を超える変更を通さないこと。相互レビューで最も危ないのは、
内容を分からないまま承認することなので。

### 3. 自分の PR に来た指摘に応える

- コードで応えるか、なぜ直さないかをコメントで返す
- **直して push すると approve が外れる**（`dismiss_stale_reviews_on_push`）。
  レビューを依頼し直す。**`gh pr edit --add-reviewer` は上と同じ理由で落ちる**ので
  REST を使う

  ```bash
  gh api -X POST repos/:owner/:repo/pulls/<n>/requested_reviewers -f 'reviewers[]=<相手>'
  ```

  **相手がレビューを出した時点で依頼は消える。** つまり指摘を受けて直した PR は
  必ず依頼が空になっている。詳しくは CONTRIBUTING.md
  「レビュー依頼は『出したか』ではなく『いま飛んでいるか』で見る」
- 会話スレッドは resolve する（`required_review_thread_resolution` が有効）

### 4. 新しい仕事を取る（手が空いているときだけ）

着手してよいのは、次を**すべて**満たす issue のみ。

- ラベル `agent:ready` が付いている
- assignee が空
- ラベル `judgment` が付いていない
- ラベル `P0` が付いていない

## 着手の手順

1. `gh issue edit <n> --add-assignee @me --add-label "agent:wip"`
2. **必ず再確認**する。`gh issue view <n> --json assignees`
   自分以外が入っていたら、即座に自分を外して撤退する（同時着手の競合回避）
3. ブランチを切る。`<種別>/<英小文字とハイフンの短い説明>`
   （`feat` / `fix` / `docs` / `refactor` / `chore`）
4. 実装する
5. `make check`（lint + test + e2e）を通す
6. `gh pr create` で PR を出す。テンプレートの項目を埋める
7. アサインは1人に絞る。レビュー依頼は他のエージェントに出す
8. 連絡帳 #148 に1行追記する
9. **作業ログ #149 に人間向けの説明を書く**（下記の型で）

## 止まって聞くこと

次に当たったら、勝手に進めない。

- データモデルを変える必要が出た
- ADR を1枚足すべき判断をした
- 差分が 400 行を超えそう

- 本番 / staging のデータを触る操作が要る
- issue の前提そのものが間違っていると分かった

`agent:blocked` を付け、連絡帳 #148 に
`@NAKAHARA-Yuki 判断がほしい: <何を迷っているか>` と書いて待つ。推測で進めない。

## 絶対にやらないこと

- `main` へ直接 push
- **自分の PR を自分で approve する**（GitHub が拒否する。他人の approve を必ずもらう）。
  **他人が approve した自分の PR を自分でマージするのは構わない。**
  むしろそうしないと「approve 済み・未マージ」が溜まる（#111 が5日間そうなっていた）
- 他人がアサインされた issue / PR に手を出す
- **ETL ワークフローを dev 以外（staging / prod）に対して実行する。**
  ETL 用のサービスアカウントは `bigquery.dataEditor` がプロジェクト単位のため
  **staging と prod にも書ける**（#144）。`target` の取り違えがそのまま事故になる。
  なお `make etl` は手元から実行できない（コンテナから取得元に到達できない。#127）
- `agent:ready` が付いていない issue の着手
- 内容を理解しないまま approve する
- 推測でモデル名・API 仕様・データの中身を書く（動かして確かめる）
- **作業ログを書かずに PR を出す・マージする**（人間が追えなくなる）

## 連絡帳 #148 への報告

```
[<自分のアカウント名>] YYYY-MM-DD HH:MM <状態> #<番号> <一言>
```

状態は `START` / `PR` / `REVIEWED` / `FIXED` / `BLOCKED` / `IDLE` のいずれか。
状況が変わらない周回では書かない。

## 作業ログ #149 への記録（人間向け）

**PR を出したときと、PR がマージされたときに必ず書く。**

読み手はコードを読まない人。**ここだけ追えば状況が分かる状態を保つ。**
これを怠ると、人間が置いてけぼりになって判断できなくなる。

### 書き方の決まり

- **専門用語を使ったら、その場で1行で言い換える**
  例:「PROPERTY GRAPH を作り直しました（＝制度どうしの関係をたどる索引の再構築です）」
- **ファイル名・カラム名・関数名を説明の主語にしない**
  「`effective_max_age_months` を修正」ではなく「年齢の上限が正しく効くようにしました」
- **利用者から見て何が変わるかを最初に書く。** 変わらないなら
  「利用者から見た変化はありません」と明記する。変化がないことも情報
- 全体で3〜6行。長くしない
- 数字は、何と比べていくつなのかを添える
- 迷ったら、専門用語を1つ減らす方を選ぶ

### 型

```
## YYYY-MM-DD HH:MM <一言で。何が変わったか>

**何が変わるか**
（利用者から見た変化。無ければ「利用者から見た変化はありません」）

**なぜやったか**
（どの困りごとが解消されるのか）

**気をつけた点**
（「本来対象の人に出なくなる」「対象外の人に出てしまう」に関わるなら必ず書く）

**あなたに決めてほしいこと**
（無ければ「ありません」と書く。省略しない）

PR #<番号> / issue #<番号>
```

## リードの追加責務

リード（@NAKAHARA-Yuki）は上のループに加えて、毎周回で次も行う。

1. **連絡帳 #148 で BLOCKED になっているものに答える**（最優先。ワーカーが止まっている）
2. 自動で片付けられそうな issue に `agent:ready` を付ける
3. **1日1回、作業ログ #149 にその日のまとめを書く**

### `agent:ready` を付けてよい issue の条件

- 何をすれば完了かが issue 本文だけで判断できる
- `judgment` ラベルが無い（ADR 0001 の制約に触れない）
- `P0` でない
- データモデルの変更を伴わない
- 差分が 400 行に収まる見込み

**迷ったら付けない。** 付けなければ誰も手を出さない。

### 1日のまとめの型

```
## YYYY-MM-DD のまとめ

**今日入ったもの**
- <利用者から見て何が変わったか>（PR #___）

**進行中**
- <何をやっているか。いつ頃終わりそうか>（#___）

**決めてほしいこと**
1. <質問。選択肢があるなら並べて、おすすめを書く>
（無ければ「ありません」）

**うまくいかなかったこと**
（あれば正直に書く。無ければ省略）
```

何も進まなかった日も「今日は進みませんでした」と書く。
沈黙は「順調」とも「止まっている」とも読めてしまうため。

### リードが実装するとき

リードの PR も、他のエージェントの承認が要る（自己承認は通らない）。
**判定ロジックに触れる PR を出すときは、レビュー依頼のコメントで
「どこを重点的に見てほしいか」を明示する。** 見る側に判断材料を渡すこと。

## 安全弁

追加のブランチ保護設定は入れていない。既存の仕組みで足りる。

- `main` は承認1件必須、GitHub は自己承認を許可しない
  → **誰の PR も、必ず本人以外の目を通る**
- `judgment` ラベルの issue は自律の対象外
  → 判定ロジックの仕事を自分から取りに行く経路が無い
- 作業中に判定ロジックへ触れる必要が出たら止めて聞く

残る risk は「エージェントが書き、別のエージェントが承認して `main` に入る」経路。
これは受け入れたうえで、**作業ログ #149 で人間が事後に追える**ことを担保にしている。
だから作業ログを書かないことは、規約違反というより仕組みの破壊にあたる。

## 止め方

| 状況 | やること |
|---|---|
| 新規着手を止めたい | `agent:ready` を全部外す。着手中のものは続く |
| いま動いているものも止めたい | 各セッションで esc、または「作業を止めてください」 |
| 緊急 | `docker stop kosodate-agent-<name>` |
| 出てしまった PR を消す | `gh pr close <n>` してブランチを消す |

`main` には自己承認では入らないので、**最悪でも PR 止まり。**
